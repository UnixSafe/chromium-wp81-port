# Build progress and open blockers

These are local experiments against Chromium `159.0.8154.13` on 20 and 21 November 2026. They are neither a release nor a device test.

## Verified locally

- The current patch passes `git apply --check` against the corresponding pristine Chromium source. It contains no Microsoft SDK files or Google Chrome branding.
- An ARM32 `winuwp` / Phone 8.1 graph generates with GN: 36,378 targets from 5,010 files, with Skia's optional Dawn backend disabled. The cross-build now uses the **Windows Phone 8.1 SDK headers and ARM import libraries**, extracted from Microsoft's Visual Studio ISO. The SDK files stay outside this repository.
- With precompiled headers and Control Flow Guard disabled for Phone 8.1, Ninja builds `message_pump_win.obj`, `object_watcher.obj`, and `waitable_event_win.obj` against that Phone SDK. The `IFrameworkView` shell entry point and `BrowserMainRunnerImpl` compile as ARM32 Thumb COFF objects with the same headers, using their GN compiler commands directly. BoringSSL entropy, zlib, Abseil time zone and random seed, Protobuf IO, and selected Perfetto components also compile against the Phone SDK.
- The configured `base` target now builds to `obj/base/base.lib` with `ninja -j6`. It is a thin static archive containing ARMv7 Thumb COFF objects, not a linked executable. The Phone-only graph omits desktop-only token, GDI, shell, ETW and stack-profiling units. New file, Mojo, clock and thread Phone paths use the `WINUWP_8_1` plus `WINAPI_FAMILY_PHONE_APP` guard. Clock, thread creation, COM apartment queries and file operations use APIs available in the Phone SDK; unavailable telemetry returns an error or empty result.
- Targeted builds now also compile WebRTC network and threading units, libjpeg, BoringSSL key-provider adapters, Mojo's local data-pipe and external-channel adapters, ICU's data and timezone units, Expat, FreeType, HarfBuzz, and selected Skia raster and file adapters as ARMv7 Thumb COFF objects. Unsupported cross-process Mojo handle transport and named-pipe server functions fail explicitly. FreeType's optional environment property override is disabled on Phone; no system font discovery or display test exists.
- The Phone `content_shell` graph excludes Crashpad and uses Chromium's existing disabled crash-key implementation. GN inspection found no Crashpad target among its 14,338 transitive dependencies after this change; the browser will have no Crashpad reports. Skia's XPS and desktop DirectWrite sources are excluded. Its ARM32 raster pipeline and semaphore objects compile, but rendering on the phone remains untested.
- The entry point invokes `content::ContentMain` with `--single-process`. The UI pump dispatches through `ICoreDispatcher`. The IO pump uses a waitable event for task scheduling. `ObjectWatcher` uses `WaitForMultipleObjectsEx` and returns notifications to the owning sequence.
- Chromium's default TCP backend uses `WSAEventSelect` and the event watcher. The Phone SDK exposes `WSAEventSelect`; the shell's configured HTTP cache is in memory. In-process Mojo message pipes exist. HTTP response bodies use Mojo data pipes; a Phone-only process-local ring backend now compiles into ARM32 objects. A small host test verified zeroed storage, producer/consumer visibility, wraparound and data survival after producer destruction. The backend refuses serialization across a transport. No full HTTP request or phone runtime has been tested.
- ICU data, V8 startup data and `.pak` resources now use a 64 MiB-bounded immutable copy reader on Phone. The relevant ARM32 objects compile. Writable and transportable shared mappings still fail explicitly. A `.pak` gzip read also enforces its decompressed output limit.
- Four V8 generators (`mksnapshot`, Torque, bytecode builtins, regexp special case) were built for a Linux IA32 host with six parallel Ninja jobs. The macOS GN graph launches them through a network-isolated Docker runner and verifies 19 matching V8 target configuration values before use. The `run_mksnapshot_default` GN action produced `snapshot_blob.bin` (2,891,236 bytes, SHA-256 `2cd16fca6c54f96453ab953a6e4e459530e4cf4e2877b5ff3f979dd49a18aa1f`), `embedded.S` (13,910,875 bytes), and `builtins-effects.cc` (131,411 bytes) for Windows ARM32. These are generated assets, not an executable browser. A previous direct Linux host experiment also assembled the embedded output into a 5.4 MB ARMv7 Thumb COFF object.
- A Phone-specific SQLite VFS replaces desktop-only filesystem hooks with app-local `ApplicationData` paths, `CreateFile2`, and byte-range file locking. The associated SQLite shim, VFS path adapter, and Chromium file ID adapter compile as ARM32 objects. Database open, transaction recovery, and locking behavior remain untested on the phone.
- QUIC address conversion uses Phone-compatible Winsock numeric-name APIs, and the Phone UDP path compiles without unavailable QoS headers. Optional DSCP/ECN controls return an unsupported result. The Phone WebRTC graph selects upstream C implementations instead of GNU ARM assembly incompatible with the MSVC-style ARM target. Targeted ARM32 builds passed for these changes; media and network behavior remain untested.
- Phone-specific UI objects use WinRT `IUISettings::AnimationsEnabled` and a conservative BGRA8/D3D11 SDR color-space path. They compile as ARM32 objects. There is still no `CoreWindow` presentation, touch, or font validation. Mojo file handles and simdutf CPU detection also compile with Phone-compatible API paths.
- The Phone network notifier uses `Windows.Networking.Connectivity` rather than desktop IP Helper or Network List Manager APIs. It queries the active connection profile, receives status changes, and reports interface addresses from WinRT host names. The factory and three ARM32 objects compile. Wi-Fi, mobile data and airplane-mode transitions have not been observed on the phone; IPv4 interface indices are unavailable through this adapter.
- TLS verification uses Chromium's built-in root store on Phone, without accepting arbitrary phone trust decisions. Portable NTLMv2 compiles with explicit credentials. The phone's personal certificate store, local trust settings, client certificate authentication, and Kerberos are not integrated. The proxy service defaults to direct routing; system proxy discovery is unavailable. These paths compile in targeted probes, while full network integration remains untested.
- Phone DNS keeps Winsock `getaddrinfo` and `freeaddrinfo`. Since the Phone SDK does not expose the desktop DNS server and suffix configuration, Chromium uses its system-resolver path and invalidates cached results after WinRT connectivity changes. The relevant ARM32 objects compile; actual DNS traffic has not been tested. The ordinary TCP path uses Winsock event notifications rather than IO completion ports. Its ARM32 objects compile, without an end-to-end connection test.
- The Phone graph excludes the blockfile cache, which requires writable memory mappings. Chromium's simple disk cache remains the persistent-cache backend, and its Phone file rename helper compiles. An explicit request for blockfile fails before touching its files. The cache has no device transaction or persistence test.
- Desktop ETW tracing is excluded from the Phone browser graph; the Perfetto trace path remains. GN inspection confirms that `content_shell` does not depend on `tracing_etw`. A desktop-only target retains an empty GN placeholder for whole-graph generation, but is not part of the Phone browser.
- The Phone shell now contains a `CoreWindow` Aura host, D3D11/DXGI presenter, WinRT touch adapter, and a shell-owned address bar with Back, Reload, Go and an ASCII touch keyboard. The address bar defaults bare hosts to HTTPS and removes credentials from the displayed active URL. Its navigation and touch objects compile as ARM32 Thumb COFF. Integrated host compilation waits for generated Mojo headers and has not displayed a frame or navigated on the phone. It currently targets one active view at a maximum of 30 frames per second; physical rotation, IME, Unicode input and actual touch behavior remain untested.
- The Phone `ui/gfx` graph now uses DirectWrite 1 to enumerate installed fonts and Fontations to decode the font bytes. WinRT supplies scrollbar width and text scale where available. A targeted Ninja build completed eleven affected ARM32 Thumb COFF objects, including the font manager, fallback and window-manager adapters. GDI regions, desktop HWND and D3D11.4 fence units are excluded. No glyph has been rendered on the handset.
- An [import audit](building.md#checking-phone-sdk-imports) finds eight selected symbols in the actual Phone 8.1 ARM import libraries, including `CreateFile2`, `GetOverlappedResultEx`, `RoGetActivationFactory`, `D3D11CreateDevice`, `CreateDXGIFactory2`, and `DWriteCreateFactory`. This checks import names, not runtime behavior.
- A native Phone 8.1 ARM [package template](packaging.md) now has a parseable manifest, correct-size image assets, an `internetClient` capability and a packaging recipe. The Phone VC120 framework is distinct from the desktop ARM framework. The template has not been packed or signed because there is no linked browser executable.

## Build and runtime blockers

- No Chromium browser executable has linked. The `base` static archive builds, but this does not validate its symbols against a final executable. Twelve incremental `content_shell` attempts with `ninja -j6 -k10` advanced from the first failure at 130 of roughly 38,800 steps to 5,225 steps in the latest completed attempt. The twelfth run stopped on 14 desktop GDI/HWND and font objects in `ui/gfx`; targeted Phone replacements now compile. The thirteenth run reached 4,196 of 37,470 steps without a `FAILED` line and was stopped deliberately for a pause; its end is neither a success nor a product error. On 21 November 2026 Ninja reported `premature end of file; recovering` for `.ninja_deps` and dropped dependency records for roughly 4,700 already-compiled objects. This explains why successive runs restarted near the same total instead of resuming. `ninja -t recompact` produced a log that loads without the warning, and a fourteenth broad run started from 37,470 dirty steps. Running any other Ninja command against the same `out/` directory while a build writes is the likely cause and is now avoided. The fourteenth run stopped at 2,430 of 40,545 steps on 13 libvpx ARM32 assembly units: they use ADS/armasm syntax, and no armasm is available to this cross-build. The Phone graph now selects libvpx's portable C configuration (`source/config/win/generic`, high bit depth, `CONFIG_MULTITHREAD 0` because the Phone SDK lacks `WaitForSingleObject` and `CreateSemaphore`, VP8 threading units omitted). `libvpx.lib` and `libvpxrc.lib` build as ARM32 static archives; VP8/VP9 software decoding is single-threaded and unoptimized and has not run. A fifteenth broad run follows. Runs fifteen to seventeen then stopped, in turn, on desktop display code, ANGLE and dav1d. On Phone, `ui/display` now keeps only its DPI and text-scale helpers plus a zero-result EDID stub, because the shell installs a `ScreenBase`; `ScreenWin`, `HMONITOR`, GDI, display-configuration, ICC and WMI units are excluded. The fling scheduler and HDR proxy use the generic path there. PDH CPU probing and `GlobalMemoryStatusEx` tracing samples are disabled, and a DXGI test placeholder uses `CreateEventExW`. ANGLE no longer forces `WINAPI_FAMILY_PC_APP` on Phone; its D3D backends are disabled, and the common utilities report failure for the current-directory, temp-file, module-path and process-time helpers. dav1d uses a C-only `config/win/arm` (`HAVE_ASM 0`) with `CreateThread`/`WaitForSingleObjectEx`. `ui_display.lib`, `system_cpu`, `libGLESv2_thin_static.lib` and `dav1d.lib` build as ARM32 archives; none of this is linked or tested. Builds twenty and twenty-one ran with `ninja -k 0` to list every remaining failure at once (943, then 810 objects). The Phone graph had lost its `wp81_linux_v8_tools` argument, so V8's generators were being rebuilt for the macOS arm64 host, which V8 rejects for an ARM32 target; restoring it removed those 138 failures. Args now also disable VR/OpenXR, Dawn, WebNN's TFLite/LiteRT runtimes, media remoting and mDNS. FFmpeg has a derived portable-C `winuwp/arm-neon` configuration (all architecture and assembly flags off, `HAVE_UWP` and `HAVE_WINRT` on, desktop console/module/mapping APIs off); `getenv` and `GetFullPathNameW` are bypassed under `HAVE_UWP`, and `ffmpeg_internal.lib` builds for ARM32. The Windows D3D11/D3D12/Media Foundation backend of `media/gpu` is excluded on Phone, which uses the GPU media client stubs; this also removes libaom from the graph. Audio and video playback remain untested. On Phone, `//sandbox/win:sandbox` keeps only its public interfaces with a factory that returns no broker and no target, and `sandbox/policy` uses `sandbox_win_phone.cc`, where every policy operation reports `SBOX_ERROR_UNSUPPORTED`. The package process is already an AppContainer, and with no broker services `Sandbox::Initialize` returns early for the unsandboxed browser. Both archives build for ARM32; renderer isolation remains absent, as with `--single-process`. V8's immediate-crash sequence now uses `__debugbreak()` for Windows ARM32 under clang-cl instead of the x86 `int3`. TFLite, which `media/webrtc` depends on unconditionally, builds for ARM32 after Phone guards in gemmlowp and tsl (`GetNativeSystemInfo`, no `GetModuleHandleW`), TFLite (`LoadPackagedLibrary`, no psapi memory query), ruy (no environment), fxdiv (portable `UMULL` under clang-cl), Eigen (`<intrin.h>`), pthreadpool (a Win32 SRW-lock/condition-variable backend instead of C11 threads, which VC120 lacks) and cpuinfo (Windows ARM32 reported unsupported, no standard-handle logging). None of these paths has run on the device. LLVM cannot emit Windows C++ exception handling for ARM32 (`WinEH not implemented for this target`), so on Phone libc++ is built with Chromium's `no_exceptions` config like every other target; `exception_ptr` is always null there and rethrowing aborts. libc++ also keeps the global `_WIN32_WINNT=0x0603` on Phone and uses `CreateFile2`, `FILE_ID_INFO`, `FindFirstFileExW`, `FileBasicInfo` and statically linked `WaitOnAddress`; links, the current directory, `readlink`, `canonical` and `temp_directory_path` report `ERROR_NOT_SUPPORTED`. `GetThreadId`, `SwitchToThread` and `GetACP` are declared explicitly because `WindowsPhoneCore.lib` exports them while the application-partition headers hide them. `libc++` now builds for ARM32; its behaviour on the phone is untested. No actual `CoreWindow` display or device font path has been validated.
- The cross-build still mixes Phone 8.1 headers/import libraries with a newer Visual C++ CRT. A controlled ARM link probe shows modern inline `sprintf_s` requests `__stdio_common_vsprintf_s`, absent from VC120, whereas the VC120 headers call exported `sprintf_s` and link. The Visual C++ 2013 Phone ARM libraries and the matching signed `Microsoft.VCLibs.120.00.Phone` package were recovered from Microsoft's ISO, but no executable exists yet. A symbol audit of the 6,294 ARM objects compiled so far found 28 external symbols that only the modern CRT defines: aligned and sized `operator new`/`delete`, `_Init_thread_header`/`_footer`/`_epoch` (thread-safe statics), `__tls_guard` and `__dyn_tls_on_demand_init` (dynamic `thread_local`), `__std_exception_copy`/`_destroy`, `__std_type_info_compare`/`_name`, `std::uncaught_exceptions`, `__stdio_common_vsprintf`/`vsnprintf_s`/`vfprintf`/`vsscanf`/`vswprintf`, `__acrt_iob_func`, `_sopen_dispatch`, `_wsopen_dispatch`, `_wchdir`, `_set_new_mode` and `_set_new_handler`. VC120 exports no C99 `vsnprintf` (only `_vsnprintf`, which does not terminate truncated output), so a global `_NO_CRT_STDIO_INLINE` would only move the failure to link time. The planned remedy is a link-time Phone compatibility library implemented on VC120 exports and Phone SDK primitives, with a check of whether VC120 `printf` parses the C99 `%z`, `%j` and `%t` size prefixes that Chromium uses; it is not written yet. The `basic_ostream` sentry is the only `std::uncaught_exceptions` consumer found: under `WINUWP_8_1` it now calls the VC120 boolean predicate `?__uncaught_exception@@YA_NXZ` and keeps the exact `== 0` meaning. A targeted ARMNT `stringprintf.obj` compiled with this header imports exactly that symbol, which VC120's Store `msvcrt.lib` maps to `msvcr120_app.dll`. It is a compiled object, not a linked library.
- Phone AppContainer headers reserve IO completion ports for desktop code. `RegisterIOHandler` and `RegisterJobObject` return `ERROR_NOT_SUPPORTED` under WINUWP. Direct IO completion port consumers include Mojo's external channels, file streams, blockfile disk cache, serial IO, and an experimental TCP backend. The event based default TCP path and memory cache avoid those particular consumers, but a full navigation trace is still needed.
- The Phone SDK reserves `CreateFileMapping`, `MapViewOfFile` and `UnmapViewOfFile` for desktop or PC apps. The immutable resource reader covers three startup consumers; other mappings and any cross-process shared buffer still have no Phone implementation. The process-local Mojo data-pipe ring has only an isolated test, so a real network response and the complete Mojo endpoint lifecycle remain unverified.
- A Phone `CoreWindow` presentation path exists in source, but its integrated host has not compiled, and display, touch, fonts and GPU behavior need device validation. The APPX template has not yielded a package or signature, and there is no validated sideload path. The connected device was identified in read-only diagnostics as a **Lumia 920 RM-821**, despite the initial Lumia 925 description.
- The Phone shell now also passes `--disable-software-rasterizer` after `--disable-gpu`, so the compositor uses its CPU path without probing WARP or SwiftShader. `BrowserMainLoop::InitializeToolkit` skips `InitCommonControlsEx` and `<commctrl.h>` on Phone 8.1 while still creating the Aura environment. Neither change has been compiled into a linked browser yet.
- Installation path: Microsoft's developer registration service is closed, and a USB-visible phone is not a sideload-enabled phone. Documentary review found only one route reported to work on a Lumia 920 running Windows Phone 8.1: WPinternals bootloader unlock, mass-storage mode and root access ("jailbreak"). It is not a full flash, but it rewrites the boot chain (GPT, SBL2/SBL3/UEFI, and partitions copied from the FFU) and needs a community engineering SBL3. WPinternals itself warns that a failed unlock may require reflashing a stock ROM. Enterprise AET signing, portal emulation and WP8.1 interop exploits are unavailable or unproven. Nothing has been written to the phone, and the exact OS build has not been read yet.
- `--single-process` removes renderer isolation. The Phone port explicitly rejects child-process creation and disables protected-memory hardening, WebAssembly, TurboFan and Temporal. Battery and memory telemetry, version-resource inspection and ETW tracing are currently unavailable. The OS info adapter reports the Phone 8.1 API level, with a conservative single-processor value and no observed build number; these placeholders must be revisited before a release. Even if it starts, it will not have full compatibility with current sites.

No phone storage or firmware was modified. The device has not executed any of these objects.
